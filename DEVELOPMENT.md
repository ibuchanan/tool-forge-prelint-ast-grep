# Development

This is the contributor guide for developing and testing rules in this
repository. If you just want to _use_ the rules in a Forge app, see the
[README](README.md) instead.

## Prerequisites

- Node.js and npm (or Bun for running the package scripts)
- Mike Farah yq v4 (tested with v4.54.1), Bash, jq, and shasum for authoring checks

## Setup

```sh
npm install
```

There's no build step — the rule files are the shipped artifact.

## Repository structure

```
rules/<tier>/<category>/*.yml          rule definitions
rule-tests/<tier>/<category>/*.test.yml  matching valid/invalid test cases
rule-tests/__snapshots__/              auto-generated match snapshots
rule-tests/fixtures/repo-init-forge-app/ legacy zero-findings fixture
fixtures/drop-calf-forge-app/           default forge-app tooling generated by Drop Calf
sgconfig.yml                           dev-only config covering every rule dir
sgconfig.<tier>.yml                    the four shipped tier configs
scripts/check-fixtures.sh              runs the fixture regression check
scripts/release-prepare.sh             cuts a release (see Releasing below)
cliff.toml                             git-cliff config for CHANGELOG.md generation
```

`<tier>` is one of `recommended`, `strict`, `atlassian`, `ecosol`.
`rule-tests/fixtures/repo-init-forge-app/` models a fully repo-init-compliant
Forge app; it must produce zero findings when scanned with
`sgconfig.ecosol.yml` — `npm run test:fixtures` enforces this.

`fixtures/drop-calf-forge-app/` is the verbatim default `forge-app` tooling
output from the vendored Drop Calf module. It starts from an empty directory,
so it has no manifest, source, or registered app identity. To refresh it, use
a fresh empty input directory (outside the fixture), then export locally:

```sh
mkdir -p tmp_rovo_drop_calf_input
dagger call -m ./vendor/ranch-rig-drop-calf init-changes \
  --directory ./tmp_rovo_drop_calf_input \
  --profile forge-app --owner tester --package-name sample \
  export --path ./fixtures/drop-calf-forge-app
```

Remove the empty input directory afterward. `npm run test:fixtures` checks the
generated Biome hard exclusion, but does not require the whole snapshot to be
finding-free: the Fence Rider migration findings are deferred. Review a full
`ast-grep scan --config sgconfig.ecosol.yml fixtures/drop-calf-forge-app` when
refreshing it. The snapshot is excluded from Prettier to preserve generator
output exactly.

## Development loop

```sh
npm test             # rule tests + fixture regression check
npm run format:check # prettier --check
npm run check        # both of the above
```

To regenerate snapshots after changing a rule:

```sh
npm run test:update
```

To step through mismatches interactively:

```sh
npm run test:interactive
```

## Adding or changing a rule

The [rule-authoring policy](docs/reference/rule-authoring-policy.md) specifies
metadata, inline rating rationale, composable scope profiles, and the reviewed
severity matrix. The [glossary](GLOSSARY.md) distinguishes categories, tiers,
profiles, and ratings. New and migrated rules follow that contract; existing
unmigrated rules remain compatible during the documented rollout. Ticket 01
introduces the policy and a metadata-only pilot. Ticket 02 provides explicit
[yq metadata recipes](docs/how-to/backfill-rule-metadata.md), shared constants in
`authoring/policy.yml`, and opt-in preservation tests:

```sh
bash scripts/test-rule-metadata.sh
```

These need Bash and Mike Farah yq v4 (tested with v4.54.1), not a custom CLI or
JavaScript/TypeScript runtime. The small sourced tool guard does not edit files.
Automatic scope inference, prose URL extraction, and assessment/companion reports
are deliberately out of scope. Ticket 03 adds repository-only native self-checks
and a frozen legacy allowance. `npm test` (also the existing pre-push/CI entry
point) runs them after consumer tests and fixtures. Run them independently with:

```sh
bun run test:authoring
# Check explicitly selected rule documents without editing them:
bash scripts/check-authoring.sh rules/recommended/package-json/require-package-private-true.yml
```

The [self-evaluation reference](docs/reference/rule-authoring-checks.md) lists
checked invariants, exit statuses, supported scope comparisons, migration
allowances, and remaining review responsibilities. A `REVIEW:` line is not
validated scope compliance. Scope normalization and severity changes require
their later, explicit reviews.

1. Add or edit the `.yml` rule file under `rules/<tier>/<category>/`.
2. Add or update the matching test file under
   `rule-tests/<tier>/<category>/`. Every rule change needs a matching test —
   this is enforced by convention, not tooling, so don't skip it.
3. Run `npm run test:update` to (re)generate the snapshot, then `npm test` to
   confirm everything passes, including the fixture regression check.
4. If the rule applies to the `ecosol` tier, make sure
   `rule-tests/fixtures/repo-init-forge-app/` either already satisfies it or
   is updated to satisfy it — that fixture must stay a zero-findings example
   of full compliance.

`scripts/check-security-fixtures.sh` runs as part of the fixture suite. It copies
text fixtures from `rule-tests/fixtures/security/` into a temporary app and checks
TS/TSX/JS/JSX and module-extension routing, tier inclusion, Custom UI outside
`frontend`, source exclusions, and manifest/package filename restrictions.
The temporary app is removed on exit; the `.txt` sources keep YAML fixtures out
of the rule-test discovery path.

`ast-grep test` has a few sharp edges worth knowing before you hit them:

- `valid`/`invalid` entries must be plain strings — there's no way to give a
  test case a synthetic file path, so a rule's `files:`/`ignores:` glob is
  untestable via `ast-grep test`; only the `rule:` node-matching logic itself
  is exercised.
- Every `.yml`/`.yaml` file under `rule-tests/` is treated as a test-case
  file, including anything under `rule-tests/fixtures/`. Don't add a
  `.yml`/`.yaml` fixture file (e.g. a realistic `lefthook.yml`) — it will be
  misparsed as a broken test case and fail the whole suite.
- A rule with `severity: off` can't be loaded by `ast-grep test` at all, so
  it can't have a test file. This is by design for intentional placeholder
  rules, not a bug to work around.

## Releasing

```sh
npm run release:prepare
```

This bumps the version in `package.json`, regenerates `CHANGELOG.md` via
`git cliff`, commits, tags, and pushes `main` plus the new tag — review the
diff before running it, since it pushes on your behalf.
